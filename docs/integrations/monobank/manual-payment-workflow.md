# Sellora AutoSales — ручне підтвердження оплати без банківського API

**Мета:** зберегти робочий шлях Instagram Direct → клієнт → замовлення → квитанція → перевірка фактичного надходження в mono ФОП → позначення `PAID` → ТТН/відправка, не підключаючись до рахунку банку. Клієнт не отримує повідомлень від Sellora.

## Реалізований сценарій

1. Менеджер або власник створює **реальне товарне замовлення** Sellora для відомого клієнта. Для Direct є наявні механізми зв'язку клієнта/замовлення, але створення замовлення не вважається автоматично доведеним до завершення #386.
2. Клієнт надсилає квитанцію у Direct; менеджер переглядає її самостійно, звіряє суму, покупця, замовлення і реквізити. **Картинка не підтверджує надходження.**
3. Менеджер окремо заходить у mono ФОП і **перевіряє фактичний зарахований платіж** та його унікальний ідентифікатор.
4. У **Замовлення → Деталі → Ручне підтвердження оплати** вибирає `BANK_IBAN`, `FOP_CARD` або `MONO_ACQUIRING_LINK`. Уводить унікальний **ID банківської операції** (не номер картки, IBAN чи токен), відмічає **обидві** перевірки й підтверджує.
5. Backend перевіряє permission MANAGER+, workspace, UAH, реальну неархівну картку замовлення, клієнта та товарні позиції, точну **повну** суму й можливість записати транзакцію тільки один раз у workspace.
6. У **одній транзакції БД** створюється незмінний ручний record, журнал audit з ім'ям актора і `payment_status=PAID`. Якщо замовлення раніше вже мало `PAID`, запис перевірки додається ретроспективно, але його дохід не перераховується і не дублюється.
7. Після цього менеджер продовжує звичайний процес чеку/створення ТТН/відправки.

## Обмеження

- `manual_payment_confirmations` — **людська заява про перевірку**, не автентифікована API виписка і не гарантія від помилки/шахрайства. Sellora не перевіряє, чи дійсно банк зарахував гроші.
- Немає читання персональних API/merchant токенів, не створюються платежі, повернення чи повідомлення клієнтам.
- **Тільки повне одноразове зарахування**, точна сума замовлення, валюта UAH. Partial, overpayment, refund, disputed, historical, cancelled, returned та COD мають залишатися на ручному розгляді, без автоматичного `PAID`.
- Запис має унікальні обмеження `(workspace_id, order_id)` та `(workspace_id, transaction_reference)` — повтор запиту безпечний, один і той самий ID не можна використати двічі для одного workspace.
- Generic `PUT /orders/{id}` більше **не переводить уже існуюче замовлення в PAID** без окремого підтвердження. Водночас статус `PAID` досі можна задавати при **створенні** замовлення в інших існуючих сценаріях (наприклад, fulfillment), і він може означати **непідтверджену окремим журналом оплату**: картка це явно показує.
- Після ручного підтвердження generic редагування забороняє мовчки повертати `PAID` у `PENDING/COD/REFUNDED`: потрібна окрема audited correction/refund-функція, якої в цьому етапі ще немає. Не виконуйте виправлення грошей через SQL.
- Квитанція зараз **переглядається людиною**, автоматичного витягування номера з медіа/AI OCR немає. Примітка до квитанції є лише ручним коротким посиланням, а не доказом зображення.
- Поточні звіти Sellora можуть враховувати погоджений дохід за етапом замовлення незалежно від дати оплати; ручне підтвердження не створює нового рядка виручки і не перераховує прибуток.

## Технічний контракт

`GET /api/v1/orders/{order_id}/manual-payment`: MANAGER+, повертає record (або `null`) тільки у своєму workspace, приховує raw transaction ID.

`POST /api/v1/orders/{order_id}/manual-payment/confirm`: MANAGER+, JSON:

```json
{
  "payment_method": "BANK_IBAN",
  "transaction_reference": "bank-operation-id-example-001",
  "amount_minor": 74900,
  "receipt_checked": true,
  "bank_received_checked": true,
  "receipt_note": "Квитанцію перевірено в Direct"
}
```

Заборонено `bank_verified` / `provider_verified` та інші недокументовані поля. Помилки бізнес-правил повертають 409, відсутнє замовлення — 404.

## QA критерії

- Відсутній прапорець квитанції **або** фактичного надходження → `PAID` не змінюється.
- Wrong workspace/права ANALYST/несинхронізоване, скасоване, історичне, COD замовлення → відмовити.
- Сума = exact `order.revenue * 100`, а UAH включено → record, audit, `PAID`; без змін SKU, кількості, резервів, доходу, собівартості.
- Duplicate reference іншого замовлення → 409; повтор ідентичного запиту → один запис.
- Existing `PAID` без ручного доказу → дозволити людську атестацію без другої виручки.
- No bank API keys, webhooks, outgoing transfers, automatic refunds or outbound Direct messaging.

**Наступні етапи:** індексація квитанцій у Direct, partial/refunds, автоматичне створення лише достовірних itemized orders (#386), підтвердження банком після авторизації (#395).
