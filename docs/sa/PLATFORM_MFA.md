# MFA для операторів Sellora Platform Admin

Оператор входить із паролем і підтверджує доступ до Platform Admin шестизначним TOTP із застосунку-автентифікатора. Це потрібно для всіх платформних ролей. Після підтвердження клієнт тримає доказ у пам’яті вкладки до 30 хвилин. Оновлення access token зберігає доступ у тій самій сесії. Перезавантаження сторінки потребує нового коду. Звичайні CRM API використовують чинну авторизацію.

Сервер шифрує секрет TOTP окремим ключем Fernet. Підтвердження зберігається як SHA-256 у записі сесії й передається лише в заголовку платформних запитів. Скасування сесії, відкликання або повторна видача platform grant та заміна чи видалення фактора припиняють дію попереднього підтвердження. Код приймається один раз на оператора. Після п’яти невдалих спроб діє обмеження до кінця п’ятихвилинного вікна.

## Захищений staging

1. Зафіксуйте поточні захищені frontend і backend deployments для відкату. Перевірте, що upstream вказує на виділений staging API і тестову БД.
2. Встановіть у staging backend секрет `SELLORA_PLATFORM_ADMIN_MFA_KEY` із незалежним ключем, створеним за допомогою `Fernet.generate_key()`. Збережіть той самий ключ для довіреного термінала реєстрації. У середовищі `production` увімкнений Platform Admin завжди вимагає MFA. Для тестового середовища з іншою назвою встановіть `SELLORA_PLATFORM_ADMIN_MFA_REQUIRED=true`.
3. Застосуйте Alembic `202611130058` через роль міграцій. Для staging із окремою runtime-роллю `noevia_backend` застосуйте до нової таблиці наведені ACL та RLS. Реєстрація й видалення фактора виконуються через довірену роль, що має право змінювати записи фактора й сесії та додавати записи аудиту.
4. Зареєструйте фактори для операторів і перевірте їхній доступ до призначення deployment на staging-домен.
5. Розгорніть frontend і backend з одного перевіреного дерева, збережіть чинний захист Vercel і перевірте вхід оператора, відмову без коду, повторне використання коду, доступ звичайного CRM-користувача та вихід.

```sql
GRANT SELECT ON public.platform_operator_mfa TO noevia_backend;
GRANT UPDATE (last_step, failure_count, window_started_at)
    ON public.platform_operator_mfa TO noevia_backend;
CREATE POLICY noevia_backend_mfa_select ON public.platform_operator_mfa
    FOR SELECT TO noevia_backend USING (true);
CREATE POLICY noevia_backend_mfa_update ON public.platform_operator_mfa
    FOR UPDATE TO noevia_backend USING (true) WITH CHECK (true);
```

Ці дозволи потрібні runtime для читання зашифрованого фактора, блокування його рядка й обліку спроб. Перевірте також UPDATE для `auth_sessions.platform_mfa_digest` і `auth_sessions.platform_mfa_expires_at`. Якщо для `auth_sessions` видано лише поколоночні дозволи, додайте до них SELECT та UPDATE для цих двох колонок. `anon`, `authenticated` та `PUBLIC` не отримують доступ до таблиці факторів.

## Реєстрація, заміна та відкликання

Запустіть із каталогу `backend` у приватному терміналі без запису екрана чи виводу. Для кожного оператора потрібні власний пароль Sellora та його застосунок-автентифікатор.

```bash
PYTHONPATH=. python scripts/manage_platform_mfa.py enroll \
  --operator OPERATOR_UUID --approval-ref APPROVAL_REFERENCE
```

Додайте показаний ключ у застосунок як TOTP і підтвердьте налаштування поточним кодом. Для першого входу після реєстрації дочекайтеся наступного коду. Повторний `enroll` замінює фактор. Команда `remove` з тими самими параметрами видаляє фактор і відкликає його підтвердження. Аудит фіксує дію та посилання на погодження без кодів, секретів або підтверджень.

Під час відкату збережіть схему та записи факторів. Повернення до попереднього backend без MFA допустиме лише після вимкнення Platform Admin або блокування доступу до нього на рівні захищеного staging. Якщо втрачено ключ Fernet, зареєструйте нові фактори з новим ключем.
