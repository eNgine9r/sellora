## Межа доступу

Platform Admin залишається модулем наявного FastAPI і Next.js. Тонкий API делегує policy та use cases сервісам, SQL залишається в репозиторіях. Окремі platform DTO проєктують дозволені поля. `PlatformWorkspaceRepository` робить обмежений глобальний пошук тільки по метаданих `workspaces` і дозволених проєкціях. Detail, activity та subscription передають цільовий UUID у scoped-запити. Чинні tenant API й repository scopes зберігають власні правила.

- Запропоновані `platform_operator_grants` і `PlatformGrantRepository` з одним записом на `user_id`, окремим enum ролей, станом, часом видачі та відкликання. Видалення або деактивація акаунта припиняє доступ. Дозволи визначає статична матриця, а активний grant перевіряється в БД на кожному запиті. JWT і workspace role можуть ідентифікувати користувача у відповідних чинних потоках, але джерелом platform-дозволу є тільки grant.
- Спільна перевірка JWT повертає підтверджений контекст сесії. Для platform потрібні чинний `sid`, активний користувач і серверна ознака успішного прямого входу з паролем. Запропоноване nullable `auth_sessions.authenticated_via` встановлює тільки прямий login, refresh зберігає значення, legacy upgrade і старі записи залишаються без ознаки. Старі сесії потребують повторного входу для доступу до платформи. У SA.1 перевірити, що цей additive контракт зберігає чинні tenant login, upgrade, refresh і revoke.
- Default-off прапорець `SELLORA_PLATFORM_ADMIN_ENABLED` повертає `404` до доступу до даних. Далі відсутня або нечинна автентифікація дає `401`, відсутній дозвіл дає `403` до lookup цілі, відсутня дозволена ціль дає `404`. Backend і transport не використовують `X-Workspace-ID` для platform scope. Ціль визначає path-параметр або валідований фільтр з перевіркою дозволу.
- Початковий grant та подальша видача/відкликання виконуються аудитованою операторською командою за межами HTTP з перевіреною ідентичністю виконавця, наявним активним акаунтом-ціллю та посиланням на погодження. Початковий bootstrap одноразовий, серіалізований транзакційним lock і збереженим маркером завершення. Tenant-реєстрація, workspace owner і platform UI не видають grant. SA.5 додає контрольовану процедуру відновлення доступу.
- Внутрішня гілка UI має окремий layout, ключі кешу, залежні від ідентичності оператора, очищення при logout/зміні акаунта й обробку `401/403`. Повторно використати авторизацію, refresh і UI primitives. Platform transport відкидає workspace header навіть під час retry. Сервер виставляє `Cache-Control: private, no-store` для platform responses, включно з помилками. У UI виключити статичний і спільний кеш.

| Дозвіл | `PLATFORM_ADMIN` | `PLATFORM_SUPPORT` | `PLATFORM_AUDITOR` |
| --- | --- | --- | --- |
| `platform.access` | ✓ | ✓ | ✓ |
| `workspaces.read`, `subscriptions.read` | ✓ | ✓ | — |
| `activity.read` | ✓ | ✓ | — |
| `subscriptions.manage_trial` | ✓ | — | — |
| `security.audit.read` | ✓ | — | ✓ |

Platform grants дають тільки можливості цієї матриці. Доступ до CRM потребує чинного tenant-членства. Platform DTO виключають склад замовлень, дані клієнтів, повідомлення, контактні поля користувачів, credentials, інтеграційні секрети та raw audit payloads. Масовий експорт, impersonation, деактивація магазинів і редагування tenant-команди поза SA.1–SA.5.

## API та persistence

Шляхи нижче відносні до `/api/v1/platform-admin`. Назви нових компонентів наведено для реалізації. Чинні модулі з таблиці вище залишаються базою повторного використання.

| Етап | Контракт | Сервіс / репозиторій та міграції |
| --- | --- | --- |
| SA.1 | `GET /me` → ID оператора, роль і capabilities | `PlatformAccessService`, `PlatformGrantRepository`, `PlatformAuditRepository`. Additive міграція для grants, platform audit та session provenance |
| SA.2 | `GET /workspaces`, `GET /workspaces/{workspace_id}`, `GET /workspaces/{workspace_id}/subscription` | `PlatformWorkspaceService`, `PlatformWorkspaceRepository`, чинний `SubscriptionRepository` і `describe_subscription`. Міграція за замовчуванням зайва |
| SA.3 | `GET /activity/summary`, `GET /workspaces/{workspace_id}/activity` | `ProductEventService`, `ProductEventRepository`, `PlatformActivityService`. Additive `product_events` |
| SA.4 | `POST /workspaces/{workspace_id}/subscription/commands` після погодження політики trial | `PlatformSubscriptionCommandService`, scoped write-методи в чинному `SubscriptionRepository`, повторне використання platform audit. Additive версія та журнал ідемпотентності для команд |
| SA.5 | `GET /audit-events` з редагованою DTO, фільтрами і pagination | `PlatformAuditService` використовує SA.1 repository. Додатковий індекс за результатами вимірювання |

- List endpoints повертають до 50 записів за замовчуванням, максимум 100. Cursor непрозорий, прив'язаний до фільтрів і сортування. Базовий порядок `created_at DESC, id DESC` або `occurred_at DESC, id DESC` для activity. Фільтри мають явні allowlists і bounded time range. Пагінація keyset, з вузькими SELECT та без N+1. Стан підписки для всієї сторінки обчислюється з одним `as_of` у UTC.
- Workspace DTO — ID, назва, slug, активність, час створення й тип demo, визначений серверною provenance. Detail може включити валюту, часовий пояс і скорочений стан підписки. Перелік фільтрується за активністю та демо-типом, пошук за назвою/slug/точним UUID. Деактивовані магазини доступні з явним фільтром.
- Єдиний Alembic head у зафіксованій базі — `202611120055`. Кожен етап повторно читає актуальний head і прив'язує до нього additive міграцію. Перевірити upgrade на порожній та заповненій ізольованій PostgreSQL і least-privilege/RLS під реальною роллю застосунку. Для backend-only таблиць перевірити відсутність прямого читання клієнтськими ролями і фактичний доступ app role. Розгортати schema перед увімкненням функції. Rollback вимикає функцію та повертає сумісний код. Окремо перевірити відновлення даних перед будь-яким destructive downgrade.

## Platform audit

`platform_audit_events` зберігає UTC-час, тип та ID оператора за наявності, роль, action/outcome, тип і ID цілі, nullable workspace UUID, correlation ID і типізовані мінімальні зміни. Ідентифікатори в журналі є знімками з незалежним від hard-delete життєвим циклом. Події охоплюють grant/revoke, привілейовані читання списків і деталей, доступ до самого журналу, спроби доступу автентифікованих суб'єктів без дозволу та команди підписки. Анонімні відмови й високочастотні повтори фіксуються в bounded security telemetry без request body, токенів або клієнтських ідентифікаторів.

- Зміна стану й успішний аудит комітяться разом. Привілейоване читання даних повертає результат після збереження аудиту. Якщо збереження недоступне, операція завершується без розкриття даних або зміни стану. Відхилена команда пише мінімальну подію окремою транзакцією після rollback, з контрольованою телеметрією на випадок збою аудиту.
- Audit read записує власну access-подію один раз після отримання сторінки. DTO повертає дозволені поля й не віддає необроблені JSON-значення з tenant `audit_logs`. Runtime роль має append/read лише за потрібним шляхом. Планове видалення за погодженим retention використовує окрему maintenance-процедуру. Тривалість retention затвердити до staging-пілоту SA.5.

## Product events

- Початковий каталог `workspace.created`, `lead.created`, `order.created`. Джерела — `WorkspaceService.create_workspace`, `LeadService.create`, окремий [Direct producer](../../backend/app/services/direct_lead_service.py) та підтверджені сценарії `OrderService.create`. У SA.3 зафіксувати coverage реальних call sites і перевірити вкладені потоки з `commit=False`. Звичайне створення workspace і demo seed мають різні шляхи. Демо й історичний [імпорт](../../backend/app/services/import_center_service.py) виключені з початкових метрик.
- Envelope — `id`, `workspace_id`, `event_type`, `schema_version`, `source`, стабільний `source_key`, `occurred_at` та `recorded_at` у UTC. `occurred_at` означає серверний час бізнес-дії, незалежний від імпортованої дати сутності. Унікальність `(workspace_id, event_type, source_key)` дедуплікує ту саму бізнес-подію навіть через інший writer. Для create ключ — UUID створеної сутності. Дані мінімальні та типізовані, без вільного payload. У UI відображати час, тип і джерело. Клієнтський ingestion відсутній.
- Writer додає подію до тієї самої SQLAlchemy-транзакції. Щоб recoverable помилка аналітики не ламала CRM, producer після flush доменних записів додає подію всередині savepoint, без окремого commit. Помилка rollback savepoint або основної транзакції йде чинним доменним шляхом. Для відновлюваного збою лише event insert збільшує лічильник dropped і оновлює стан якості даних. Дедуплікований повтор не є втратою. Цю поведінку перевірити на PostgreSQL до ввімкнення writer. Writer default-off і керується окремо від platform UI.
- Summary використовує UTC-інтервали `[from, to)` і максимум 31 день на запит. Активні магазини — `COUNT(DISTINCT workspace_id)` за подіями `lead.created` або `order.created`. Нові магазини, ліди й замовлення — кількість відповідних дедуплікованих подій. Глобальна відповідь містить агрегати, workspace timeline явно scoped. Повертаються початок покриття, склад джерел і retention. Стан якості спирається на зафіксовані вікна роботи writer та спостережувані втрати. Непокритий, degraded або невідомий інтервал позначається як частковий чи недоступний. Історичний backfill поза scope.
- Початкові індекси `(workspace_id, occurred_at DESC, id DESC)` і `(event_type, occurred_at, workspace_id)`. Короткий запит по обмеженому інтервалу є початковим рішенням. Щоденні rollups або partitioning розглянути за виміряним обсягом і latency. Визначити retention та видалення подій при видаленні workspace до ввімкнення writer. Product events не використовуються як джерело фінансових показників або security audit.

## Керування підпискою

- Джерело терміну — `workspace_subscriptions`. `workspaces.subscription_plan` залишається legacy-полем. `describe_subscription` зберігає `UNMANAGED` для відсутнього рядка, UTC `[start, end)`, derived `PENDING/EXPIRED`, негайний `CANCELED`, відсутність grace для `PAST_DUE` і `enforcement_enabled=false`. [Чинний контракт](../subscription-foundation.md)
- Запропоновані внутрішні команди для погодженого pilot trial — `START_TRIAL` зі стану `UNMANAGED`, `EXTEND_TRIAL` для поточного `TRIALING` з пізнішою кінцевою датою, `END_TRIAL` для поточного `TRIALING` зі станом `CANCELED`. Поточний платний або історичний керований запис жодна команда створення trial не перезаписує. Код плану, ліміт тривалості, eligibility, допустимі reason codes і правила відмови затверджуються до відкриття write-path. За відсутності погодження доступне читання з SA.2.
- Команда приймає `Idempotency-Key`, `expected_version` і структурований reason code, повертає новий стан та версію. Відсутній термін має expected version `0`. Існуючі рядки отримують початкову версію через additive міграцію. Idempotency journal має унікальний ключ `(actor_id, idempotency_key)`, fingerprint з workspace/action/version/нормалізованими полями та мінімальну відповідь для replay. Той самий fingerprint повертає початковий результат, колізія або stale version дають `409`. Актуальний доступ перевіряється перед replay.
- Транзакція перевіряє та блокує grant оператора, серіалізує записи через workspace row lock навіть за відсутності терміну, перевіряє версію та перехід і комітить термін, idempotency result та platform audit разом. Запис потребує активного non-demo workspace і недавнього прямого входу, вік якого визначається від `auth_sessions.created_at`. SA.4 узгоджує допустимий вік сесії. Для активних legacy або непогоджених планів UI показує чинний стан і вимикає редагування.
- Paid activation, renewal, refund, PSP, checkout, webhook та entitlement enforcement потребують окремої комерційної політики й верифікованих платіжних доказів. Trial-команди не створюють платіжних receipts. Platform UI не віддає ідентифікатори merchant/transaction або raw provider data.
