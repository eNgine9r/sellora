# SA.3 — Аналітика використання Sellora

## Події та джерела

| Подія | Коли фіксується | Ключ ідемпотентності у workspace |
| --- | --- | --- |
| `workspace.activated` | `WorkspaceService.create_workspace` зберігає новий звичайний магазин і членство OWNER | UUID магазину |
| `product.first_created` | `ProductService.create_product` зберігає товар, а в каталозі немає іншого товару. Архівовані та раніше імпортовані товари також враховуються під час перевірки першості | UUID магазину |
| `order.first_created` | `OrderService.create` зберігає неісторичне замовлення, а в магазині немає іншого неісторичного замовлення. Архівовані замовлення також враховуються під час перевірки першості | UUID магазину |
| `order.created` | `OrderService.create` зберігає неісторичне замовлення, включно зі сценаріями, де commit належить зовнішній транзакції | UUID замовлення |
| `integration.used` | Успішний live sync Meta Ads, ручне отримання розпізнаного статусу Нової пошти або успішна перевірка з'єднання Instagram. Повтор того самого провайдера в один UTC-день зводиться до однієї події | Код провайдера та дата UTC |

Демо-магазини виключені за чинною серверною audit provenance. Джерела обмежені зазначеними точками. Автоматичне відстеження відправлень, імпорт історичних замовлень, читання Direct та пасивні перегляди сторінок не є джерелами. Попередню активність не заповнюємо заднім числом. Телеметрія містить workspace UUID, тип, джерело, внутрішній ключ дедуплікації, версію схеми та час. Полів для довільного payload немає.

## Розрахунок

| Метрика | Формула |
| --- | --- |
| Активні магазини | Кількість унікальних workspace з принаймні однією з наведених продуктових подій |
| Дні активності | Кількість унікальних пар workspace і UTC-день з продуктовою подією. У профілі магазину це кількість його активних днів |
| Активовані магазини | Сума `workspace.activated` |
| Перші товари | Сума `product.first_created` |
| Перші замовлення | Сума `order.first_created` |
| Створені замовлення | Сума `order.created`. Перше замовлення входить у цю суму один раз |
| Дні використання інтеграцій | Сума унікальних пар провайдер і UTC-день у кожному workspace. Два провайдери одного дня дають два спостереження |

Дані для запиту беруться з `product_usage_daily`, згрупованої за workspace, UTC-днем і типом події. Запис події та зміна лічильника атомарні. Звіт охоплює сьогодні до `as_of` та попередні 6 або 29 UTC-днів. `from_day` і `to_day` включні. Активні магазини за подіями та увімкнені магазини реєстру мають різні джерела.

Графік і таблиця «Замовлення за днями» використовують `daily` з тих самих API активності. Кожен елемент містить UTC-день, кількість нових замовлень і кількість зафіксованих втрат телеметрії. У покритий день без замовлень API повертає 0. Дні до початку покриття відсутні в ряді. Сума добових значень дорівнює «Створені замовлення» за період. Позначка неповного дня означає зафіксовану втрату продуктових подій цього дня.

## Покриття й експлуатація

- Writer за замовчуванням вимкнений. Для запуску потрібні `SELLORA_PRODUCT_USAGE_CAPTURE_ENABLED=true` і `SELLORA_PRODUCT_USAGE_COVERAGE_FROM` з часовим поясом. Встановіть час фактичного початку захоплення. Перший неповний UTC-день виключається зі звіту.
- `complete` означає, що запитане вікно входить у задекларований інтервал збору і в ньому немає записаних втрат. `partial` означає неповне вікно або зафіксовану втрату. `unavailable` повертає `totals=null` при відсутньому покритті або для демо-магазину. Нуль показується тільки в доступній частині вікна.
- Відновлювані збої телеметрії відкочують її savepoint. CRM-транзакція може завершитись звичайним шляхом. Друга коротка спроба зберігає лічильник `capture.dropped`. Якщо це також неможливо, лог містить загальне повідомлення без ідентифікаторів. Після перерви або втрати маркера оновіть межу покриття до фактичного відновлення writer.
- Події та агрегати видаляються разом із workspace. Доступ до таблиць відповідає наявному backend-only RLS, а читання API потребує `activity.read`. Перед увімкненням у середовищі перевірте доступ app role до обох таблиць. Вікно читання обмежене 30 днями. Політика вікового очищення потребує окремого узгодження.
